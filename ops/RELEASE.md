# NM-AI-05E.1 cloud-only release decision

**BLOCKED for hosted release.** The existing private GitHub Free repository and the verified staging setup do not provide an independent approval and execution boundary. The Operations branch runs credential-free CI. The former local release CLI now always fails closed. This decision supersedes the local runner, signed SSH tag, local scheduler and activation-marker instructions in earlier commits and application-side deployment documentation.

## Cloud-only architecture to qualify before enabling

Use an **already approved, independently administered cloud release control plane**. It could use a GitHub-hosted runner in an existing, separate private control repository with Founder-exclusive workflow and credential access, or an existing isolated cloud service that owns both release execution and durable state. No application or operations writer may modify the control plane, administer its identities, influence a credentialed execution context, or read its secrets. If no such surface is available at zero incremental cost, retain the hold. No new service is assumed or provisioned.

1. **Request and approve.** A requester supplies application SHA, operations SHA, staging account/database/Worker, phase and maintenance evidence. The control plane validates a Founder-authenticated approval via the provider API, including the immutable account ID, exact request and expiry. It independently requires QA approval for the exact application SHA and successful CI runs from the expected repositories, workflow paths and events for both SHAs. Use CI as evidence of checks, not as release authority. Protect the control-plane code and approval entrypoint from project writers. A project PR comment, commit author field or untrusted workflow result cannot approve a release.
2. **Consume and audit.** Store the verified approval, executor version, exact artifact digest and result in a durable store inaccessible to project writers. Atomically consume the one-time request and lock the staging target before granting access to credentials. Retry and acceptance require separate approvals. A stale approval or ref/commit/artifact change invalidates the run. An ephemeral runner filesystem, GitHub cache, project artifact or editable issue is not this store.
3. **Isolate execution.** Use only a pinned, independently reviewed release executor and exact, verified inputs. Keep credentials in the control plane and separate from application-controlled workflows, build hooks and dependency installation. Pass approved artifacts as data across the boundary. Verify release-eligible artifact contents and provenance before publication. Never send a Cloudflare credential back to a runner controlled by a project writer.
4. **Quiesce and preserve.** Require separately approved maintenance and record the current Worker version, public/preview/custom routes, schedules and target identities. Disable ingress and schedulers, check alternate routes, service/queue bindings and direct D1 writers, drain mock/in-flight work and independently observe stable bookmarks and data. Refuse writes if any evidence is missing. Persist and authenticate encrypted Time Travel evidence before migration, with the key in separate access-controlled storage and artifact TTL at most seven days. Verify production and staging IDs are distinct, apply only ordered pending 0003–0005 after ledger 0001–0002, and check ledger, fingerprints, FTS, usage and foreign keys before the deploy marker. Restoration of D1 requires separate approval.
5. **Restore the route safely.** A successful upload alone must not reopen staging. Keep the maintenance barrier in force while verifying exact Worker version, D1 and AI bindings, previews disabled and Messenger ingress/outbound false. The published application configuration has workers.dev and schedules enabled, so the executor must publish a maintenance-safe deployment or hold an independent ingress/scheduler barrier through verification. Only then restore the recorded staging route and approved schedules, and verify the exact release marker, signed-out API denial, Messenger webhook denial and final control-plane state. Do not blindly restore the previous runtime after a schema change. If verification fails, keep the barrier in place and request a separate incident decision. Hosted acceptance retains the original scoped 13+2 benchmark.

## Threat model and Founder configuration

Project writers can mutate refs, CI definitions and workflow inputs and can try to trigger old, new or rerun jobs. They cannot impersonate the provider-authenticated Founder account unless they compromise that account, and a qualified control plane must never trust their self-reported actor/approval data. GitHub log masking does not stop a credentialed malicious workflow. Cloudflare account administrators and independently trusted release-control administrators remain privileged. A durable ledger cannot prove that unknown direct D1 writers stopped. These risks must be addressed by actual access controls and maintenance evidence, not an approval checkbox.

**While blocked**, in the application repo open **Settings → Actions → General → Workflow permissions** and confirm the read-only default. Under **Settings → Environments → nepmui-staging** and **Settings → Secrets and variables → Actions**, inventory live staging credentials and inherited organization access without displaying values. Keep those credentials out of the project repo's Actions and review historical queued runs. Establish safely authorized remediation separately if access remains. No credential rotation is part of this change.

**Before reconsidering**, Founder must identify the existing zero-cost isolated executor and durable store, verify exclusive admin/credential access against an actual project-writer test account, configure Founder identity validation, expiry, single-use approvals and recovery TTL, and demonstrate with synthetic evidence that a writer cannot mint or consume approval, run credentialed code or extract secrets. Then independently review the exact operations implementation and test the maintenance-safe publication and route restoration without touching hosted D1. No verified executor, store, maintenance-safe deployment or approved configuration is available for setup now. Do not add deployment secrets, configure a bypass or activate the old marker.
